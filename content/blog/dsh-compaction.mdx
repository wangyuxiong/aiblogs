# 上下文满了怎么办：DSH 的压缩经济学

![封面](/images/dsh-compaction-cover.png)

128K 的上下文窗口，看着很像一间大仓库。

真让 Agent 写一周代码，你会发现仓库里堆的不只是对话。

一次构建日志几千行，一张截图又占一笔视觉 token。

文件读取、测试报错、补丁 diff，都在悄悄吃掉窗口。

等提供方返回上下文溢出，工作还没做完，历史先放不下了。

我读完 DSH 2.0.22-next 的压缩相关文档后，最关心的反而不是摘要写得好不好。

真正有意思的是它怎么记账：哪些内容给模型看，哪些证据留在日志，哪些成本值得付。

## 一、压缩不是删除，是换一份视图

DSH 的上下文压缩叫 compaction。

它把较早的一段历史换成一条摘要，近期对话则逐字保留。

下一次请求不再带着几十条旧消息，而是带着一份检查点继续工作。

这就是它的经济模型：用一份摘要，换多份原始输入。

但这里有两个世界，必须分开看。

模型看到的是会话表层，审计和回放依赖的是原始日志。

压缩成功时，表层只发生一次变更。

一条 `user/message` 执行 replace，承载新的摘要。

`compaction/*` 事件都只写日志。

它们不会作为额外消息混进模型历史。

被替换的旧事件也没有从日志里抹掉。

回放时，系统仍能根据替换关系，重建当时那份压缩后的对话。

所以，原始日志永远保留，不等于模型记忆永远无损。

模型拿到的是摘要，原文留给了审计、恢复和确定性回放。

这个区别很重要，否则很容易把压缩误解成免费又无损的记忆术。

## 二、它什么时候动手

DSH 有四种进入压缩的路径，处理的压力并不相同。

### token 压力越过阈值

自动检查发生在请求派生之前。

`ctx.tokenMeter` 先给当前表层和路由请求定价。

压力越线后，系统先尝试修剪，再决定是否生成摘要。

如果修剪后已经回到预算内，摘要调用可以直接省掉。

### 提供方确认上下文溢出

有时估算没拦住，提供方还是拒绝了请求。

适配器把可识别的失败规范化为 `CONTEXT_WINDOW_EXCEEDED`。

后端随后尝试最大范围的平衡头部缩减。

只有表层替换确实前进，才允许重试原请求。

### 人主动输入 /compact

`/compact` 不等阈值，适合阶段收尾时主动整理上下文。

它不是模型工具，也不消耗一个模型轮次。

不过，生成摘要仍是一笔独立的模型调用。

Agent 正在轮次中，或另一份压缩正在运行时，命令会报告暂不可用。

### 请求准备切换到另一个模型

模型切换最容易被忽略。

DSH 会先按目标模型的窗口、输出预留和压力策略测量旧历史。

如果目标装不下，就先压缩，再放行目标请求。

默认写摘要的是原路由模型，不是即将接手的新模型。

显式配置摘要提供方和模型时，才优先使用那个目标。

失败则报 `MODEL_SWITCH_COMPACTION_FAILED`，并保留原请求头。

## 三、默认值里藏着两笔预算

很多人只看到 0.8，就以为窗口用到 80% 必定压缩。

实际公式还要减去输出预留和额外余量。

```text
T = floor(min(W × thresholdRatio, W − O − headroomTokens))
R = (W − O) × retainRatio
```

W 是上下文窗口，O 是本次请求的输出预留。

T 是触发阈值，R 是近期历史逐字保留预算。

默认参数如下。

- `thresholdRatio: 0.8`：压力阈值使用的窗口比例。
- `headroomTokens: 65536`：输出预留之外的额外余量。
- `retainRatio: 0.16`：近期历史的逐字保留比例。
- `compactionRetries: 1`：首次压缩后仍超压，再额外尝试一次。
- `maxOverflowRetries: 1`：确认溢出后的最大重试次数。

请注意，16% 的基数是 W 减 O，不是整个 W。

0.8 也不是唯一闸门，W 减 O 再减 65536 可能更早触发。

这套默认值给近期上下文留下空间，也给摘要输出和下一轮响应留余地。

小窗口模型不能照抄 65536，否则预算可能直接不成立。

DSH 因此提供 `modelPolicies`，允许按提供方和模型覆盖参数。

如果 16% 不合用，也可以改用绝对的 `retainTokens`。

两种保留配置互斥，保留预算还必须低于解析后的触发阈值。

摘要的 `maxTokens` 默认跟随解析后的余量配置。

未单独覆盖时，这个默认值就是 65536。

这个上限也包含提供方计入的推理 token，不只是可见摘要正文。

配置非法时，插件会在加载或首次使用时明确失败。

它不会拿一套放不进去的数字，硬撑着继续跑。

## 四、八段摘要，其实是一张交接单

摘要写得太像文学 recap，下一位模型很难接着干活。

DSH 的默认指令因此固定了八个部分，顺序不能变，空节也不能删。

1. `Primary Request and Intent`
2. `Key Technical Concepts`
3. `Files and Code`
4. `Errors and Fixes`
5. `Pending Jobs`
6. `Current Work`
7. `Next Step`
8. `Critical Context`

空内容统一写 `(none)`。

这份模板更像工程交接单，而不是聊天内容梗概。

它要求保留精确路径、命令、错误字符串和函数签名。

用户后来的纠正、尚未完成的工作、下一步动作，也要留下。

如果历史里已有 `<compacted-summary>`，摘要器不能原样照抄。

它要合并仍然有效的事实，丢掉过时状态，再纳入新进展。

这一点决定了多次压缩不会变成摘要套摘要。

旧检查点只是输入之一，新的检查点仍要回到同一份八段结构。

我最看重的是 `Next Step` 只允许一个直接下一步。

它逼着摘要器区分“当前该做什么”和“以后也许能做什么”。

对正在改代码的 Agent 来说，这比一段漂亮的回顾更有用。

摘要调用只把返回文本写进检查点。

推理过程和工具调用不会混入持久摘要。

如果结果没有真正缩短输入，这次替换也会被拒绝。

## 五、标记对就是锁，表层只改一次

压缩最危险的时刻，是摘要请求还在等待返回。

此时会话可能继续接收上下文，进程也可能突然退出。

DSH 没把锁只放在内存里，而是把事务写进日志。

顺序很固定。

先追加 `compaction/start`，在摘要让出控制权之前拿锁。

摘要返回后，重新验证选区是否仍然稳定。

自动压缩要求整个表层稳定，手动压缩则重新核对所选范围。

手动期间，不相关的新上下文仍可按规则追加，不必冻结整个会话。

随后记录 `compaction/summary`，执行那一条 user/message 替换。

最后恰好尝试一次 `compaction/end`，释放这把锁。

如果闭合失败，未匹配的 start 会有意留下。

后续入口看到它，就把压缩视为 busy，而不是假装上次已经成功。

旧进程生命周期留下的标记则有区别。

早于最新 `session/end-seed` 的未匹配 start 不再阻塞新会话。

![压缩标记对流程](/images/compaction-flow.png)

选区边界还有一道配对检查。

前边界由 `toolPairingBalancedBefore` 对齐。

后边界由 `toolPairingBalancedAfter` 对齐。

安全边界不能跨越一个尚未收到结果的 assistant 工具调用。

否则摘要之后，模型可能先看到孤零零的工具结果，却找不到调用来源。

缺失序号、孤立 tool/result 或损坏的表层状态，都会被拒绝。

没有可安全压缩的平衡范围时，系统宁可不改变，也不硬切。

## 六、三个辅助工具，各管一种浪费

### tool-result-pruner：先剪掉最笨的部分

工具输出经常比真正对话大得多。

默认文本超过 `thresholdChars: 8192` 时，修剪器才会处理它。

结果保留 `headChars: 4096` 的头部和 `tailChars: 1024` 的尾部。

中间放入一段固定标记，明确告诉模型这里少了一截。

![工具结果修剪](/images/pruner.png)

修剪不修改模型调用，也不发起摘要请求。

它只是确定性的字符切片，计量单位是 Unicode 码点。

这样可以避免拆开 UTF-16 代理项对，但多码点字素仍可能被切断。

完整原始工具结果仍留在日志里。

替换事件通过 `sourceEventSeqs` 指回原始事件。

前面的 `compaction/prune` 还记录旧范围的影子价格。

纯日志消费方因此能减去旧价格，不必自己重放每个节点状态。

修剪后重新定价，若压力已经消失，DSH 会跳过摘要。

它也有明显边界：只看头尾，不知道中间哪一行最关键。

字符预算同样不等于 token 预算，最后仍要交给 token meter 判断。

### image-offload：把图片换成可追踪的占位文本

图片超预算时，路由会报 `IMAGE_OFFLOAD_REQUIRED`。

插件按顺序选择图片，追加 `image/offload` 事件，然后重试。

模型看到的是占位文本，里面有附件说明和可用的只读路径。

这次重试不消耗提供方重试预算，也不会追加 `llm/retry`。

选择会跨请求、模型切换和回放持续生效。

以后预算变大，旧图片也不会自动回来。

需要原图时，仍可从占位文本给出的路径重新读取。

### token-meter：所有决定先问价格

压缩不是凭消息条数拍脑袋。

token meter 在同一个日志 revision 上，为请求 envelope 和当前表层定价。

压力判断、保留预算、范围选择，都使用这套测量结果。

模型切换时按目标模型定价，缩减验证则参考已提交路由。

拿不到提供方用量时，它会回退到字符数和结构开销的启发式估算。

所以它是决策依据，不是保证每个 token 都算得分毫不差的 oracle。

## 七、摘要请求也在省缓存钱

压缩本身要调用一次模型，这笔成本不能装没看见。

DSH 的补偿办法，是让摘要请求尽量复用提供方的热前缀。

它会逐字回放系统提示词、上次路由请求的工具和被遮蔽区消息。

这些内容与会话最后一个已路由请求保持一致。

因此，缓存可以一路复用到尾随的压缩指令之前。

真正没被缓存的，主要是最后那条指令和新生成的摘要。

如果改用另一个摘要模型，或者压缩非头部范围，这项复用就会失效。

正式替换发生后，未来请求又是另一笔账。

从第一个被替换的历史 token 开始，旧缓存无法继续复用。

压缩省的是之后每一轮的输入，不是让当前这一轮零成本。

## 八、我喜欢它的地方，是承认边界

读完这套机制，我看到的是几条很克制的设计选择。

表层只改一次，让模型视图保持简单。

原始日志永远保留，让审计和回放不必相信摘要没有遗漏。

标记对落在日志里，让崩溃留下的状态也能被下一个进程理解。

配对边界拒绝乱切，让工具调用和结果不会被人为拆开。

不可分单元则直接暴露能力边界。

如果整段历史就是一个无法安全拆开的单元，压缩可以没有动作。

系统提示词、工具声明和会话前缀，也不属于表层压缩能缩减的对象。

这比宣称“再大的历史都能压”诚实得多。

实际使用时，我会先盯着超大工具输出，因为它们最适合确定性修剪。

接着按模型窗口调整余量，别让小模型背着 65536 的默认包袱。

最后才调摘要策略，并给关键文件、错误和下一步留下可核对的记录。

上下文窗口总会满。

好的压缩机制不是假装它不会发生，而是让每次缩减都知道代价，也找得回原始证据。
