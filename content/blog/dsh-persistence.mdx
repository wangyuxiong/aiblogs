# 让 Agent 拥有“昨天”：DSH 的会话持久化机制

> 信息截至 2026-11，基于 DSH 2.0.22-next 随包文档。

## 一、进程退出以后

假设一个 Agent 已经改了半仓库代码，正在等工具返回。此时进程被杀，终端里那段对话还来不及变成完整答案。

重新打开窗口很容易。难的是知道文件改到哪一步，哪个工具已经启动，哪个结果只是没有来得及写回。

如果系统只剩最后一段模型文本，它连“刚才发生了什么”都说不清，更谈不上安全地继续。

DSH 要保存的因此不是聊天外观，而是一份能重建执行过程的历史。Agent 的“昨天”，就藏在这份历史里。

## 二、把会话变成事件日志

会话常被理解为一串消息。用户说一句，模型答一句，工具偶尔插进来几条结果。

这种表示适合阅读，却不擅长描述中断。模型文本、工具调用、步骤结束和轮次结束，本来就发生在不同时间点。

DSH 把会话写成仅追加的事件日志。每条事件属于一个 session，并带有连续递增的 seq。

一次 agent turn 可以跨过多个 turn 事件。同一次顶层工具调用产生的事件，也始终留在同一轮里。

轮次因此成为恢复时的一致性边界。系统可以重放事件，重建对话、工具状态和推进进度。

这个模型也限制了写入方。`append` 要求序号连续，不能跳过尚未发生的事件。

一旦中间缺号，重放就无法判断是事件丢失，还是写入顺序被破坏。

恢复、查询和投影都依赖这条顺序。它们不必共享内存，却能讨论同一个历史位置。

这里有个容易被略过的区别：`append` 接受事件，只代表写入路径会尽力持久化。

真正的持久性承诺来自 `flush()`。它返回成功，才表示写路径已经排空，并完成了崩溃后的持久保证。

## 三、五类方法，隔开循环与存储

DSH 在 agent-loop 和存储后端之间留了一道 seam。循环看到的是稳定服务，不需要知道文件如何编码。

服务只有五类方法。把读写的两种打开方式展开，是六种调用形态：

- `create(header)`：创建会话写句柄。
- `open(id, 'write')`：接管现有会话。
- `open(id, 'read')`：取得只读句柄。
- `stat(id)`：读取单个会话元数据。
- `list()`：列出会话元数据。
- `flush()`：排空所有活跃写句柄。

所有日志 I/O 都经过 `SessionHandle`。系统没有暴露“给某个 id 追加一段”的旁路。

已发布会话也不一定有写句柄。

agent-loop 会把实时 `session/event` 路由给活跃写句柄。

没有活跃写句柄时，事件仍在内存流动，却不会进入持久化日志。

`stat` 和 `list` 只读元数据，不必加载日志正文。

可用字段包括 header、revision、事件数和字节数。

后台批次失败时，事件仍留在待写路径，自动写入暂停。

下一次显式 `flush()` 会重试。调用方可以据此阻止后续动作。

一次服务级 `flush()` 可能面对多个句柄。

失败会聚合成 `AggregateError`，不会把部分成功伪装成全部落盘。

这道边界也体现在错误上。失败不靠一段文本猜原因，每种情况都有独立 Error 类。

- 重复写打开：`SessionAlreadyOwnedError`
- 只读句柄被修改：`SessionReadOnlyError`
- 句柄关闭后继续使用：`SessionHandleClosedError`
- 写所有权永久丢失：`SessionOwnershipLostError`
- 已提交内容损坏：`SessionPersistenceCorruptionError`

调用方可以按类型决定释放、重试或停止。JSONL 是默认后端，却不是 agent-loop 必须理解的格式。

## 四、JSONL 后端怎样落到磁盘

默认编码是 `compression: 'zstd'`。磁盘上并非一整块压缩数据，而是带校验和的独立 zstd 帧。

日志开头有一个 header 帧。之后每个 append 批次追加一个帧，并在批次完成前执行 fsync。

这也让恢复可以按帧判断边界。后一个批次损坏，不必否定前面已通过校验的内容。

选择 `compression: 'none'` 时，文件才是换行分隔的 UTF-8 纯文本 JSONL。

每个 root 只支持一种编码，不能在同一目录中靠猜测混用。

压缩方式变化需要独立 root，系统不会自动降级成另一种编码。

当前磁盘 generation 是 v3。历史 v0、v1、v2 仍能读取，并通过迁移进入当前格式。

`create(header)` 还有一层延迟实体化。它先返回内存中的写句柄，不创建目录，也不加锁。

第一次 `append` 才发布 header 和首批事件。

对空句柄执行 `flush()`，也可以只写入 header。

所以，一个从未追加或 flush 的新会话若随进程消失，它就从未在磁盘存在过。

单写者由锁兜底。POSIX 使用 `session.lock` 上的非阻塞 flock。

Windows 不使用锁文件，而是由路径派生命名内核信号量，避免留下文件系统痕迹。

后续写入若在中途失败，后端会把文件截回之前的字节长度。已提交事件不会被顺手改写。

## 五、崩溃恢复有两道工序

恢复先处理物理文件，再处理语义轮次。这两件事经常混在一起，其实各自回答不同问题。

物理层只承认为有效前缀。纯文本日志的不完整末行会被丢弃。

zstd 日志遇到撕裂帧时，只保留其中还能完整解码的 JSONL 记录，其余尾部丢弃。

写句柄在追加新事件前，会先截掉撕裂字节，再把恢复出的完整记录持久写回。

纯文本 JSONL 的边界很直观，换行就是记录分界。

zstd 则要多走一步，先从帧中取出完整记录，再判断事件是否有效。

如果损坏落在完整、已提交的帧里，例如校验和失败，系统会拒绝打开，而不是静默跳过。

文件完整了，会话仍可能停在半个轮次。最后一条事件也许是 assistant 的工具请求，却没有对应结果。

这时不能直接追加下一句模型回复。恢复方会生成 `interruptedTurnClosers`，把中断轮次闭合。

合成 closer 包含必要的 `tool/result` 错误和未闭合的 `step/end`。

最后还会补上带 interrupted 的 `turn/end`，明确这轮已经被打断。

其中两种工具结果标记，决定了后续能做什么：

- `TOOL_NOT_STARTED`：没有持久调用，工具可以视为未启动。
- `TOOL_OUTCOME_UNKNOWN`：已有调用，结果未知。

第二种情况最危险。模型只能直接重试只读或幂等工作。

涉及副作用时，必须先核实外部状态或询问用户。持久化无法证明那次调用没有生效。

只读观察方也遵循同样的轮次规则，但它只在内存中补齐 closer，不向持久化日志写任何东西。

同一份冷日志因此可以有两种结果。

写恢复会留下修复后的新事件，只读查询只改变这次观察所见的内存视图。

两者解决的是同一个语义问题，产生的副作用却完全不同。

## 六、格式迁移只能逐级走

格式升级并不是把旧文件改名。DSH 的 catalog 同时登记编解码器和相邻 migration。

构造时会校验迁移链唯一且无缺口。读取可以依次经过 v0、v1、v2，最终到达 v3。

系统只支持相邻整数版本，没有跨级 span。每一级的结构变化都有明确归属。

历史源始终保持逐字节不变。只读打开只在内存迁移，不发布新文件。

写打开才会生成后继 generation。迁移结果先写入同目录临时文件，再交给 Worker Thread 校验。

发布前还会复查源 revision，确认准备期间没有新写入，最后以不覆盖方式发布。

Worker 必须自然以退出码 0 结束。提前退出或校验失败，都不能被误当成成功。

重复打开也考虑了成本。准备结果使用按 revision 键控的有界 memo，复用解码和迁移结果。

源 revision 一旦变化，缓存立即失效。写打开不会发布基于旧 revision 的准备结果。

迁移可以流式进行，中间状态有界。

但当前事件数组和序号重映射表仍随事件数增长，不能宣称全程只占常量内存。

“流式”描述的是迁移过程，并不消除最终重建当前状态的成本。

## 七、客户端为什么还需要投影

事件日志适合恢复，却不适合直接驱动界面。一个 todo 面板没必要理解全部模型和工具事件。

投影子系统在每个 session 上折叠出当前值。客户端拿到的是经 schema 校验的完整 JSON 值。

每个领域单元提供 key、初始状态、schema、版本，以及同步的 `apply(state, event)`。

`apply` 必须同步返回，误给 Promise 会被拒绝。

view 也会经过 schema 校验，坏视图不能悄悄进入客户端。

仅供宿主使用的单元可以不暴露 wire，客户端根本看不到它。

无关事件必须返回原 state 引用。这条约束构成了第一道 `Object.is` 闸门。

state 引用没变，投影连 view 都不必重算。第二道闸门比较相邻原始 view 引用。

view 引用也没变，就抑制一次发布。新建一个内容相同的对象，仍然会被视为变化。

读取 `snapshot(session)` 时，返回值包含 `{ asOfSeq, values }`。

`asOfSeq` 指明这批值共同反映到哪条事件。

客户端看到的是一致切面，不是各自追赶的进度。

快照与分页切片在同一拍捕获，所有值都折叠到同一个最后事件。

冷读还有 checkpoint。

持久投影缓存让列表读取跳过全量日志加载，需要折叠时从检查点水位继续。

缓存只能落后于日志，不能跑在日志前面。

格式版本或 schema 不匹配时，旧缓存不会用于播种。

检查点之后的新事件仍要按序应用，结果才能标到对应的 `asOfSeq`。

列表行也不等于全量投影。

`SessionProjectionSummaryExcluded<T>` 用来标记摘要不收录的值。

对应 wire 还会声明 `summary: false`，共同排除重字段。

当前排除项包括：

- `turnOutline` 与 `sessionStats`
- `todos` 与 `imageLimits`
- `contextPressure` 与 `contextBreakdown`

需要这些值时，仍可读取完整 snapshot。列表摘要只是控制了常见路径的体积。

## 八、持久化是一组明确边界

把整套机制拆开看，几个选择彼此咬合。

仅追加让历史保留发生顺序，连续 seq 给事件定位，单写者避免两个推进者交叉改写。

flush 屏障把“已经收到”与“崩溃后仍在”分开。

模型请求、顶层工具正文和下一 agent step 前，都有相应检查点。

检查点失败会阻止后续执行。不过，它持久化的是调用意图，不承诺外部副作用恰好一次。

事件溯源让系统能够重放和修复，投影又让客户端免于重放。两种读法共享同一份权威日志。

最后还有权限边界。持久化与查询服务都不提供调用方授权。

能打开一份会话，不代表任何 UI 或模型工具都该展示它。访问控制仍由上层明确实施。

Agent 的“昨天”由此成为一套可检验的承诺：哪些事件已落盘，哪次调用结果未知，哪个视图对应哪条事件。

进程可以消失，执行历史仍有据可查。下一次打开会话，系统才知道该怎样接着走。
