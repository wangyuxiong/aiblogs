# 拆了 6 篇 DSH，我看到的 Agent 设计哲学

![DSH 系列复盘封面](/images/dsh-recap-cover.png)

过去一段时间，我沿着源码拆了六篇 DSH。

从 Agent 主循环，拆到任务调度、微内核、自治、持久化和上下文压缩。

拆完后，最吸引我的反而不是某个功能。

是几件看似分散的事，反复做出了同一种选择。

## 一、为什么拆 DSH

LangChain 和 AutoGPT 都值得研究。

它们提供了理解 Agent 生态的不同入口，这不是一篇框架优劣评比。

我选择 DSH，是因为它把一个完整 Harness 的琐碎问题都摆在了源码里。

会话怎么恢复，任务谁来写，插件怎么卸载，自动续行谁来批准。

这些问题不显眼，却会在产品上线后一起找上门。

拆框架调用链，容易看见 Agent 能做什么。

拆这些边界，才能看见它答应不做什么。

这也是六篇文章最终能串起来的原因。

文中数字与行为，以本次拆解的 DSH 2.0.22-next 及对应文档为准。

## 二、先看六篇地图

下表不是内容摘要，而是一张问题索引。

你可以从自己正在踩的坑，倒推该读哪一篇。

| --- | --- | --- | --- |

| 02 | [dsh-router-worker](/blog/dsh-router-worker) | Router 管全局连续性，Worker 管任务隔离，Engine 统一写入职责。 | 多任务并行时，谁来分派和负责？ |
| 03 | [dsh-microkernel](/blog/dsh-microkernel) | 内核只管组合与生命周期，连 Agent 主循环也能作为插件装载。 | 怎样扩展系统而不养出巨石内核？ |
| 04 | [dsh-autonomy](/blog/dsh-autonomy) | 持久状态不等于持久授权，自动续行需要明确的人类允许。 | Agent 自己跑时，边界放在哪里？ |
| 05 | [dsh-persistence](/blog/dsh-persistence) | 会话以仅追加日志为权威，恢复靠追加修复事件，不改写历史。 | 崩溃后怎样恢复，还能说清发生过什么？ |
| 06 | [dsh-compaction](/blog/dsh-compaction) | 压缩改变模型当前看到的表层，原始日志保留，缓存成本也要入账。 | 上下文满了，省什么又不能丢什么？ |

![六篇文章地图](/images/six-articles-map.png)

六篇合起来，我看见了五条贯穿始终的设计哲学。

它们比任何单个功能都更值得搬进自己的项目。

## 三、微内核加插件，让变化可以撤回

第一条是，把稳定的东西留小，把易变的东西放外面。

在我拆解的版本里，Cordis 内核是 2811 行。

里面没有 agent、model、session、llm 这些业务词。

连 Agent 主循环，也只是组合配置里的一个普通插件。

这个例子说明，主循环不是不可触碰的底座。

它和调度、持久化一样，都要遵守组合规则。

更具体的细节在卸载路径。

插件注册 effect 时，也登记对应的逆向清理。

卸载按后进先出的顺序回滚，避免依赖还活着，提供者先消失。

你可以在自己的项目里先做一次减法。

写下内核绝不承担的业务词，再为每个扩展点补卸载测试。

还要记住，可组合不等于已授权。

能安装插件是一种技术能力，允许谁安装仍是产品权限。

## 四、Router 和 Worker，把连续性与执行分开

第二条是，全局协调和具体执行不要抢同一支笔。

Router 常驻，维护全局连续性，也统一面对人。

Worker 围绕任务隔离执行，不必背起整个系统的会话关系。

一个很有代表性的细节是订阅直通。

Worker 的订阅事件可以直接送到关注方，省去 Router 的重复分派。

但这条近路只减少转发成本，不增加任何权限。

另一个细节是 Engine 的唯一写者身份。

Trigger、Thread、Decision、Ticket 和 Assignment，都由它统一提交。

accept 时原子建单，避免外部看见半张任务单。

迁移到自己的项目，可以先画出每张状态表的写者。

如果 Router、Worker 和定时任务都能改同一张单，就先别谈智能调度。

先让一个角色负责决策写入，再让其余角色提交事实和结果。

上线顺序也可以照抄这个克制。

先只观察分派建议，确认误判成本，再逐步开放自动执行。

## 五、状态不等于授权，人类在环是默认

第三条是，记住目标，不代表永远有权继续执行。

DSH 的 Goal 有持久状态，还有一个不持久的 armed 标志。

会话恢复或者 fork 后，active 目标会自动进入 disarmed。

目标还在，续行授权没有跟着恢复。

只有人类明确说继续，它才重新 armed。

创建、修改、暂停和恢复目标，也要求直接的人类消息。

顶层 Agent 才能做，子代理和调度来源不能代办。

自主 Round 可以报告完成或阻塞，但阻塞也有硬约束。

同一个条件要连续存在三轮，才允许标记 blocked。

在自己的产品里，可以把两张表彻底分开。

一张存用户想要什么，一张存当前谁允许系统继续做。

重启、迁移、fork 和权限变化时，默认收回第二张表。

这条设计会直接改变产品话术。

你说的是“我记得上次的目标”，而不是“你不用再管了”。

## 六、事件溯源加仅追加日志，让恢复有证据

第四条是，事实先进入日志，界面和模型视图都从日志派生。

DSH 的每个会话存一份仅追加 JSONL 日志。

默认用带校验和的 Zstandard 帧，已提交事件绝不重写。

写入侧也不是大家共用一个文件就完事。

进程内先做单写者认领，JSONL 后端再加跨进程排他锁。

POSIX 上是 session.lock 的非阻塞 flock。

崩溃恢复同样遵守这个方向。

中断轮次已经提交的内容会保留，撕裂尾部不会交给读方。

恢复方追加合成 closer，把工具结果和轮次结尾补齐。

它不会回头修改旧事件，假装那次崩溃没有发生。

派生视图还有两道 Object.is 闸门。

state 引用没变，就跳过 view 计算。

原始 view 引用没变，就跳过对客户端发布。

这两道小闸门把日志权威和运行效率连了起来。

你不必每次收到事件，都重算并重推整个页面。

搬到自己项目时，先指定唯一事实源，再接受缓存可以陈旧。

缓存必须能重建，不能反过来领先已提交事实。

同时写清单写者锁的作用域，别把进程内互斥误当分布式锁。

## 七、表层只改一次，原始日志永远保留

第五条是，给模型减负，不要把证据一起删掉。

DSH 把当前模型可见内容叫表层，把完整会话日志留在下面。

一次成功压缩，会用一条摘要消息替换选中的较早表层。

整个事务里，表层只发生这一次变更。

compaction 的开始、摘要和结束，全部只是日志事件。

被遮蔽的原始消息仍留在仅追加日志里。

于是回放可以重现同一份压缩后对话，审计也还有原始材料。

触发阈值同样是一笔明账。

默认取窗口的 0.8 与扣除输出、余量后的容量，两者较小值。

余量默认 65,536 tokens，近期逐字保留预算是可用容量的 16%。

它们是工程默认值，不是被证明适合所有任务的最优比例。

压缩前还可以先修剪超大工具输出。

如果压力已经缓解，就不再为摘要多付一次模型调用。

代价也没有被藏起来。

表层替换会让首个被替换 token 之后的 KV Cache 复用失效。

你在自己的项目里，也应分开保存工作视图和原始记录。

再同时测量摘要调用、输入缩减、缓存失效和任务质量。

只报省了多少 token，还不是完整的压缩方案。

## 八、这些不是架构选择，是产品承诺

把五条连起来，会发现它们都在回答用户的问题。

插件可逆，回答的是“需求变了，系统能不能改”。

Router 与 Worker 分工，回答的是“并行以后，谁对结果负责”。

状态与授权分离，回答的是“我不盯着时，它能做到哪一步”。

仅追加日志，回答的是“出了意外，我们能否还原现场”。

表层压缩，回答的是“记了很久以后，什么被保留，什么被隐藏”。

所以这些不是藏在架构图里的审美偏好。

它们最终都会变成用户听得懂的产品承诺。

而承诺必须能验收。

能否卸载，能否重新授权，能否回放，能否指出压缩范围。

答不上来，就不该只在宣传页上写可靠、自治和长期记忆。

## 九、做 Agent 产品，可以从哪篇开始

如果你只读一篇，先读 [dsh-superagent](/blog/dsh-superagent)。

它先建立全局地图，后面的拆解才不容易变成包名清单。

如果你正在做多任务产品，接着读 [dsh-router-worker](/blog/dsh-router-worker)。

重点不是角色名字，而是统一写者和权限不因近路扩大。

如果你在搭平台或插件生态，读 [dsh-microkernel](/blog/dsh-microkernel)。

重点看依赖激活和逆序卸载，不必先照搬插件数量。

如果你准备让 Agent 无人值守，读 [dsh-autonomy](/blog/dsh-autonomy)。

先把恢复后的授权体验设计好，再讨论能连续跑多少轮。

如果你在做恢复、审计和协作，读 [dsh-persistence](/blog/dsh-persistence)。

把日志、投影和缓存的关系看懂，比挑一种文件格式更重要。

如果你正被长上下文和成本夹击，读 [dsh-compaction](/blog/dsh-compaction)。

先把经济账算全，再调 0.8 或 16% 这样的参数。

更实际的一条阅读路径是 01、02、04、05、06。

需要改内核和扩展机制时，再回头精读 03。

## 十、最后，把这套哲学带进测试

我正在做的 Test AI Loop，也是这套哲学在测试领域的应用。

需求先可测化，是在缩小稳定内核，先把验收约定说清楚。

AI 生成与多信号验证分开，是不让执行者独自宣布自己正确。

多实现、负例和变异测试交叉验证，是在给结论补独立证据。

CI 归因和失败回流，保留问题如何进入修复的过程。

最后由门禁放行，是把自动修复和发布授权分开。

人仍负责需求是否说对，以及这次结果能不能出去。

这里没有把 DSH 的代码原样搬进测试产品。

被复用的是那些约束：职责清楚，证据可查，授权明确，失败能回流。

如果这六篇只留下一个阅读结论，我希望是这个。

Agent 产品真正值得设计的，不只是它能自动做多少事。

还有每一步由谁负责，留下什么证据，以及人如何重新接管。
