# Mind Keeper 个人品牌站改造设计

- 日期：2026-11-06
- 状态：已与站点所有者确认方向，待实施
- 站点：https://mind-keeper.com

## 1. 背景与问题

Mind Keeper 的目标不是做一个泛 AI 资讯站，而是一个对外展示个人能力、作品与观点，并逐步建立个人影响力的品牌站点。

当前主要问题：

1. **首页被日刊占据**：首屏、最新内容和订阅区块都围绕 AI 日报，访客难以回答“站长是谁、擅长什么、为什么值得关注”。
2. **内容结构失衡**：自动日刊数量远多于原创教程、技术复盘和项目案例，更新频率没有有效转化为个人品牌资产。
3. **项目展示偏功能列表**：现有作品集主要描述技术栈和功能，缺少问题背景、个人职责、关键决策、结果与可验证链接。
4. **关于页缺少真实身份与证据**：机器人占位图、技能百分比和设备清单不能替代经历、代表工作与明确的专业方向。
5. **更新承诺与实际存在偏差**：定时发布链路仍在运行，但 GitHub 调度可能延迟数小时；“每日更新”等文案没有展示真实更新时间，也没有区分机器整理与人工推荐。
6. **公开信任基础需要修复**：截至 2026-11-06，生产 HTTPS 证书校验失败，直接影响访问、搜索收录与品牌形象。

### 已确认的事实

- 2026-11-05 的日报已经上线，最近定时工作流均成功，不能将问题误判为“自动发布完全停摆”。
- GitHub Actions 的定时任务并不保证准点。2026-11-05 的任务计划为 00:00 UTC，实际约 04:05 UTC 才开始。
- 当前站点为 Next.js 15 + Contentlayer + MDX 的纯静态站点，保留这一低成本架构即可，不需要为品牌改造引入后端。

## 2. 品牌策略

### 2.1 定位

**AI 产品与工程实践者。**

建议对外表达：

> 我是 Mind Keeper，一名 AI 产品与工程实践者。把复杂 AI 技术讲明白，也把学到的东西做成可用工具。

品牌核心不是“这里每天有很多新闻”，而是“这个人能带 AI 学习者入门，也确实做过东西”。

### 2.2 首要读者

AI 学习者与入门读者，次要读者为 AI 开发者、产品同行及潜在合作方。

内容应优先做到：

- 概念讲得清楚，不默认读者已有深厚工程背景；
- 教程能跟着做，尽量有最小示例和实际结果；
- 项目案例展示真实过程，不堆砌术语；
- 日报帮助筛选信息，但不冒充原创观点。

### 2.3 可投入资源

每周不超过 2 小时。内容节奏必须可持续，不以高频原创为目标。

### 2.4 路线选择

采用“教程 + 作品驱动”为主、“项目日志”为辅、“日报”做持续输出与分发。

不采用“日报编辑驱动”作为品牌核心，因为单纯聚合和自动摘要难以形成差异化，也无法充分证明个人能力。

## 3. 目标与非目标

### 90 天目标

1. 首页能清楚呈现个人定位、学习路径、代表作品和原创内容。
2. 形成一条可持续更新的 AI Agent 学习路径。
3. 至少完成 6 篇原创教程或复盘、2 个真实项目案例。
4. 自动日报稳定更新，展示真实更新时间，失败可发现、可告警。
5. 生产 HTTPS、基础 SEO、移动端和可访问性达到可公开传播的状态。
6. 建立原创文章阅读、项目点击、搜索收录和回访的基础度量。

### 非目标

- 不做大而全的 AI 新闻门户。
- 不在没有实际后端时增加假邮箱订阅、假用户数据或虚构项目成果。
- 不一次创建多个空专题、空项目或“敬请期待”页面。
- 不为追求视觉效果引入重型动画、复杂 CMS 或新的运行时服务。
- 不以页面浏览量作为唯一成功标准。

## 4. 信息架构

### 4.1 导航

主导航收敛为：

- **文章**：原创教程、技术实践与项目复盘；
- **项目**：真实作品与案例；
- **日报**：自动整理的 AI 技术与产品动态；
- **关于**：个人介绍、关注方向与真实联系方式。

Logo 返回首页。保留 RSS 入口，不增加无实际用途的导航项。

### 4.2 首页顺序

1. **个人定位首屏**
   - 一句话身份与价值主张；
   - 主按钮「开始学习」，次按钮「查看项目」；
   - 可附一句当前正在研究或构建的真实主题。
2. **从这里开始**
   - 首条路径为「AI Agent：从入门到做出第一个工具」；
   - 只展示已经发布的文章，未发布内容可以列作路径说明，但不能做成死链接；
   - 内容不足时只保留一条路径，不显示空栏目。
3. **代表作品**
   - 优先展示「文心启航」和「本站日报自动化系统」；
   - 每个项目突出问题、个人贡献、关键方案与结果，技术栈作为辅助信息。
4. **最新原创文章**
   - 只展示非 `ai-daily` 内容；
   - 教程、项目复盘、技术判断可以设置精选。
5. **最新 AI 日报**
   - 展示最近 3 期及真实发布日期；
   - 明确标注“自动整理”，人工推荐使用独立标识。
6. **简短个人介绍与关注入口**
   - GitHub、RSS 和经过确认的真实社交渠道；
   - 没有真实渠道时不放空链接。

### 4.3 其他页面

- `/blog`：以原创文章为主，不再让日刊淹没教程；日刊仍由 `/daily` 完整承载。
- `/daily`：保留全部日刊，移除无法验证的“20+ 新闻源”“∞ 持续更新”等装饰性数据，展示实际期数、最近更新时间和数据来源。
- `/portfolio`：逐步改为数据驱动的项目列表，案例页按统一结构呈现。
- `/about`：用真实个人介绍、正在做的事情、代表项目和联系方式替代技能百分比与设备清单的主体位置。

## 5. 内容系统

### 5.1 三层内容

| 层级 | 内容 | 节奏 | 品牌作用 |
|---|---|---|---|
| 原创教程 / 项目复盘 | Agent 入门、AI 编程实践、真实项目拆解 | 每两周一篇 | 建立专业信任 |
| 主理人推荐 | 从近期日报选一条，补充价值、适合读者和实践建议 | 每周一次，约 15 分钟 | 形成个人判断与声音 |
| 自动日报 | AIHOT 技术与产品精选 | 每天自动 | 保持活跃、承接搜索与回访 |

机器生成内容必须标识为自动整理；人工推荐必须确实由站点所有者选择或撰写，不能自动生成后冒充人工观点。

### 5.2 第一条学习路径

**AI Agent：从入门到做出第一个工具**

建议顺序：

1. Agent 是什么，与普通聊天机器人有什么区别；
2. 用模型 API 做一个最小 Agent；
3. 给 Agent 接入第一个工具；
4. 什么时候需要记忆与 RAG；
5. 如何做基本评测、控制成本与处理失败；
6. 将 Demo 部署成可使用的小产品。

按双周一篇的节奏，约 12 周完成。后续可以根据真实项目调整题目，不为了填计划而写空泛文章。

### 5.3 可立即整理的真实案例

1. **文心启航**
   - 目标用户与原始问题；
   - 为什么选择桌面应用；
   - 个人职责与产品取舍；
   - Claude / 通义千问接入方式；
   - 关键难点、实际结果、截图与可访问链接。
2. **本站日报自动化系统**
   - AIHOT API 与内容筛选；
   - MDX 生成及第三方文本转义；
   - GitHub Actions 自动提交、构建和部署；
   - 调度延迟、失败检测与数据可信度；
   - 可公开时关联仓库或关键代码。

项目没有可验证数据时，不编造用户数、增长率或性能提升，可以使用真实的功能完成度、技术产出与经验教训。

## 6. 技术设计

### 6.1 保留现有架构

继续使用：

- Next.js 静态导出；
- Contentlayer + MDX；
- Tailwind CSS；
- GitHub Actions 构建与部署；
- 阿里云 ECS 托管静态文件。

品牌改造主要是信息架构、内容模型和页面组件调整，不需要引入数据库或服务端渲染平台。

### 6.2 内容与配置

实施时按最小必要原则调整：

- 站点身份、简介、社交链接等集中到单一站点配置，避免散落在多个组件；
- 文章可补充可选的 `series`、`seriesOrder` 字段，用于学习路径排序；
- 继续使用现有 `isFeatured` 做原创精选；
- 项目较少时先用结构化项目配置驱动列表，不急于新增复杂 CMS；
- 原创文章与日刊使用明确过滤条件，避免首页和归档再次混排；
- 首页各区块在没有内容时整体隐藏，不输出空卡片。

### 6.3 首页组件边界

建议拆分为：

- 个人定位 Hero；
- 学习路径区块；
- 代表项目区块；
- 原创文章区块；
- 最新日报区块；
- 个人简介与关注入口。

组件只接收已筛选的数据，日期排序、草稿过滤和分类过滤尽量集中处理，避免各页面逻辑不一致。

## 7. 更新机制与可靠性

### 7.1 发布目标

将自动日报的计划时间从北京时间 08:00 提前到 06:00，以吸收 GitHub 调度延迟；对外目标写为“每天 10:00 前更新”，不承诺无法保证的精确分钟。

如果后续必须保证准点，再评估 ECS cron 或外部调度触发 `workflow_dispatch`，不在第一阶段增加基础设施。

### 7.2 数据流

1. 定时任务读取 AIHOT 过去 24 小时的技术与产品精选；
2. 生成器去重、过滤、转义并生成带标记的 MDX；
3. 有变化才提交，无足够内容则明确记录“本期跳过”；
4. 构建静态站点并生成 sitemap 与 RSS；
5. 部署到 ECS；
6. 对生产页面执行发布后的自动验证。

### 7.3 错误处理

- 抓取异常、数据不足、文件已存在、无需发布必须是不同状态，不能都表现为同一种“成功”；
- 工作流摘要记录各分类抓取数量、生成日期、是否提交和部署结果；
- 单分类失败可以降级，但全部失败应使任务失败并触发 GitHub 通知；
- 自动覆盖只允许作用于带生成标记的文件，人工内容不能被覆盖；
- 发布检查失败时保留错误日志，避免线上仍旧内容而任务显示全绿。

### 7.4 展示真实状态

- 首页和日报页显示最近一期的真实日期；
- 不再用绿色呼吸灯暗示无法保证的实时状态；
- 日刊页展示数据来源和自动整理说明；
- 最近更新时间过旧时，不显示“今日已更新”。

## 8. 验证与测试

每次结构改造至少完成：

1. `pnpm install --frozen-lockfile` 与完整生产构建；
2. 首页包含个人定位、真实项目和非日刊原创文章；
3. `/blog`、`/daily` 分类过滤正确，草稿不公开；
4. 学习路径只包含已发布内容，顺序正确；
5. 项目链接、导航、RSS、sitemap 和图片无死链；
6. 新文章正文静态渲染，TOC 锚点有效；
7. 日报生成器的重复执行、数据不足、单源失败和全源失败路径符合预期；
8. 桌面与移动端检查排版、导航、按钮和可读性；
9. 部署后核验生产页面，而不是只以本地构建成功作为完成依据；
10. HTTPS 证书修复后，使用不忽略证书错误的请求验证。

## 9. 分阶段实施

### P0：公开可信度（优先）

- 修复已过期的生产 HTTPS 证书并配置自动续期；
- 同步本地与远端自动提交，避免覆盖日报；
- 修正不准确的更新时间与来源宣传。

### P1：品牌首页与项目展示（约 2–3 天）

- 完成首页信息架构和站点 metadata；
- 原创文章与日刊分离；
- 项目列表结构化，补齐真实案例信息；
- 重写关于页主体；
- 完成移动端、链接与生产构建验证。

### P2：学习路径与更新可靠性（约 1–2 天）

- 增加最小必要的系列字段与路径展示；
- 调整自动日报调度；
- 增加任务摘要和生产发布后检查；
- 用真实内容验证空状态与异常状态。

### P3：90 天内容执行

- 第 1–2 周：完成两个现有项目案例的素材整理与第一篇原创；
- 第 3–8 周：持续 Agent 学习路径，每周一次人工推荐；
- 第 9–12 周：完成路径闭环，整理精选入口，依据数据优化标题与首页顺序。

## 10. 度量方式

优先使用 Google Search Console、服务器日志和一个可选的隐私友好统计工具建立基线，不急于引入复杂分析平台。

关注：

- 原创文章与项目案例的有效阅读；
- 项目点击、GitHub 点击和 RSS 请求；
- 搜索收录与带来访问的原创关键词；
- 回访读者比例；
- 日报按目标时间发布的比例与失败次数；
- 原创数量和学习路径完成度。

90 天验收不以虚假流量数字为目标，而以“定位清晰、内容持续、案例可信、链路可靠、能获得真实读者反馈”为标准。

## 11. 实施前需要补充的真实资料

以下资料不应由实现者编造：

- 对外显示名称使用真名、网名还是两者组合；
- 可公开的个人简介、头像或替代视觉；
- 文心启航的仓库、演示、截图、下载地址与真实结果；
- 是否将本站自动化系统作为公开项目展示；
- 除 GitHub / RSS 外需要展示的社交或联系方式；
- 是否启用访问统计及可接受的服务方式。

资料未齐时，对应模块保持简洁或暂不发布，不使用占位数据上线。
